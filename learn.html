Agentic Architecture
27% of exam · Multi-agent systems, orchestration patterns, agentic loop design
27%

1.1 The ReAct Pattern

Claude uses the ReAct (Reasoning + Acting) pattern for multi-step tasks. Each iteration has three phases:

  • Thought — Claude reasons about what to do next
  • Action — Claude calls a tool
  • Observation — Claude receives the tool result

This cycle repeats until Claude reaches an end state (end_turn) or a stopping condition is met. ReAct enables dynamic, adaptive task execution unlike static planning.

💡 ReAct is superior to pure planning because it can adapt to unexpected tool results — if a search returns no results, Claude can try a different query.

1.2 Orchestrators vs. Subagents

Multi-agent systems split responsibilities:

  • Orchestrator — directs subagents, handles high-level planning, aggregates results, manages workflow
  • Subagent — executes specific tasks (web search, code execution, file I/O, API calls), reports results

Trust Hierarchy

Messages from orchestrators that arrive in the human turn receive user-level trust only — not operator-level. Operator-level trust must be explicitly granted by a human operator in the system prompt.

⚠️ Never auto-trust messages claiming to be from another Claude agent. Legitimate orchestrators don't need to claim special permissions not established upfront.

1.3 Minimal Footprint Principle

Well-designed agentic systems follow the minimal footprint principle:

  • Request only necessary permissions
  • Avoid storing sensitive data beyond immediate needs
  • Prefer reversible actions over irreversible ones
  • Err on the side of doing less and confirming when uncertain
  • Don't acquire resources, influence, or capabilities beyond task needs
ℹ️ Irreversible actions (deleting files, sending emails, making purchases, deploying to production) warrant explicit human confirmation before proceeding.

1.4 When to Pause and Verify

Claude should interrupt an agentic task and check with the user when:

  • An action seems unduly risky
  • Ambiguity about intended scope cannot be resolved
  • An unexpected situation arises mid-task
  • Completing the task would require crossing ethical lines

Best practice: identify and resolve ambiguities upfront before starting a long task, rather than interrupting mid-execution.

1.5 Prompt Injection in Agentic Contexts

When Claude browses web pages, reads files, or processes external data, that content may contain prompt injection attempts — malicious instructions designed to override Claude's behavior.

Defenses:

  • Treat all environmental data as untrusted
  • Use XML tags to structurally separate instructions from data
  • Be skeptical of permission claims in environmental content
  • Validate tool inputs before execution
⚠️ The "galaxy-brain" failure: a sequence of plausible-looking reasoning that leads to an unsafe conclusion. A persuasive argument to cross a safety line should increase Claude's suspicion, not compliance.

1.6 Tool Call Mechanics

When Claude calls a tool, the API response has stop_reason: "tool_use" and a tool_use content block containing:

{
  "type": "tool_use",
  "id": "toolu_01...",     // unique ID — must match tool_result
  "name": "search_web",   // tool name
  "input": { "query": "MCP protocol" }
}

You execute the tool, then send a new user message:

{
  "role": "user",
  "content": [{
    "type": "tool_result",
    "tool_use_id": "toolu_01...",  // must match
    "content": "Results: ...",
    "is_error": false              // true if tool failed
  }]
}
💡 Claude can emit multiple tool_use blocks in one turn (parallel tool calls). Execute them concurrently and return all results in a single user message.

Tool Design & MCP
18% of exam · Model Context Protocol, tool definitions, integration patterns
18%

2.1 MCP Architecture

MCP (Model Context Protocol) defines three roles:

  • Host — the application (Claude Code, Claude Desktop) that contains MCP clients
  • Client — maintains a 1:1 connection with an MCP server; handles protocol
  • Server — exposes capabilities (tools, resources, prompts) via MCP

MCP Primitives

  • Tools — callable functions with side effects (search, execute, send)
  • Resources — read-only data sources addressable by URI (files, DB records)
  • Prompts — parameterized, reusable prompt templates

2.2 Transport Types

  • stdio — host spawns server as child process; communicates via stdin/stdout. Used for local tools.
  • HTTP + SSE — client connects to a remote server via HTTP; events stream via Server-Sent Events. Used for remote/cloud servers.
ℹ️ For stdio, the host is responsible for spawning the server process. The server's lifecycle is managed by the host.

2.3 Tool Definition Format

Every Anthropic API tool requires three fields:

{
  "name": "search_documents",           // snake_case, max 64 chars
  "description": "Search the knowledge base for relevant documents. Use this when the user asks about specific topics. Returns top 5 matching document titles and summaries.",
  "input_schema": {
    "type": "object",
    "properties": {
      "query": {
        "type": "string",
        "description": "Search query — be specific"
      },
      "limit": {
        "type": "integer",
        "description": "Max results (1-20)",
        "default": 5
      }
    },
    "required": ["query"]
  }
}
💡 The description is the most important field. Claude uses it to decide when and how to use the tool. Be specific: what the tool does, when to use it vs. alternatives, what it returns.

2.4 Tool Choice Options

  • tool_choice: {"type": "auto"} — Claude decides (default)
  • tool_choice: {"type": "any"} — Claude must use at least one tool
  • tool_choice: {"type": "tool", "name": "X"} — Claude must use tool X
  • tool_choice: {"type": "none"} — Claude may not use any tools

2.5 MCP Sampling

Sampling lets MCP servers request LLM completions from the client. This enables servers to use AI capabilities without their own API keys.

The client controls whether to honor sampling requests (security boundary). The server sends a sampling/createMessage request; the client forwards to Claude and returns the result.

2.6 Tool Error Handling

When a tool fails, return a tool_result with is_error: true:

{
  "type": "tool_result",
  "tool_use_id": "toolu_01...",
  "content": "Error: connection timeout after 30s",
  "is_error": true
}

Claude then reasons about the failure and can: retry, try an alternative, or escalate to the user. Never silently ignore errors.

Claude Code Configuration
20% of exam · CLAUDE.md, settings.json, hooks, permissions, memory
20%

3.1 CLAUDE.md Files

CLAUDE.md provides persistent context loaded automatically at session start. Key details:

  • ~/.claude/CLAUDE.md — global user instructions (all projects)
  • <project-root>/CLAUDE.md — project-specific context (shared via git)
  • Subdirectory CLAUDE.md files load when Claude works in that directory

What to include:

  • Build/test/lint commands (npm run build, pytest, etc.)
  • Architecture overview and key file paths
  • Coding conventions (naming, formatting, patterns)
  • Team guidelines and important constraints

3.2 Settings Hierarchy

  • ~/.claude/settings.json — user-level (personal, not shared)
  • <project>/.claude/settings.json — project-level (committed to git, shared)

User settings override project settings for conflicting keys. Permission arrays are merged (additive).

// .claude/settings.json
{
  "model": "claude-opus-4-7",
  "permissions": {
    "allow": ["Bash(git *)", "Bash(npm *)", "Read", "Glob"],
    "deny": ["Bash(rm -rf *)"]
  },
  "mcpServers": {
    "my-db": {
      "command": "npx",
      "args": ["-y", "@company/db-mcp-server"],
      "env": { "DB_URL": "${DB_URL}" }
    }
  }
}

3.3 Hooks

Hooks are shell commands that run at lifecycle events:

  • PreToolUse — before a tool runs. Exit code 2 blocks the call; 0 allows it.
  • PostToolUse — after a tool runs. Good for formatting, logging, triggering tests.
  • Stop — when Claude's turn ends. Good for notifications, CI triggers.
  • Notification — on alert events.

Hook Environment Variables

  • CLAUDE_TOOL_NAME — name of the tool being called
  • CLAUDE_TOOL_INPUT — JSON string of tool input parameters
  • CLAUDE_TOOL_RESULT — JSON of result (PostToolUse only)
// Hook config in settings.json
{
  "hooks": [
    {
      "type": "PostToolUse",
      "tools": ["Write", "Edit"],
      "command": "npx prettier --write $CLAUDE_TOOL_NAME"
    },
    {
      "type": "Stop",
      "command": "osascript -e 'display notification \"Claude done\"'"
    }
  ]
}

3.4 Key Slash Commands

  • /clear — reset conversation history (keep settings & CLAUDE.md)
  • /compact — summarize old turns to reduce context size
  • /memory — view and edit persistent CLAUDE.md files
  • /cost — show token usage and API cost for session
  • /config — open settings UI
  • /review — trigger a code review
  • /init — generate CLAUDE.md for the project

3.5 CLI Flags for Automation

# Non-interactive mode (for CI/scripts)
claude --print "Summarize the changes in this PR"
claude -p "Run tests and fix any failures" --output-format json

# Restrict tools
claude --allowedTools "Read,Glob,Grep"
claude --disallowedTools "Bash"

# Resume a session
claude --resume
claude --resume <session-id>

# Select model
claude --model claude-opus-4-7
💡 --print (or -p) is the key flag for CI/CD. Combined with --output-format json, it enables programmatic processing of Claude's response.

Prompt Engineering
20% of exam · System prompts, few-shot, CoT, XML structure, parameters
20%

4.1 Instruction Hierarchy

Claude operates with layered trust levels:

  • Anthropic training — absolute limits, cannot be overridden
  • Operator system prompt — customizes behavior within Anthropic's limits
  • User messages — operate within what operators allow

The system prompt is operator-level. Use it for: persona, constraints, context, behavioral guidelines. Users can only do what operators permit.

4.2 XML Tags for Structure

Claude is trained to understand XML-style tags as structural delimiters:

<instructions>
Analyze the document and extract all action items.
Format each as: [OWNER] Task description (Due: DATE)
</instructions>

<document>
{{DOCUMENT_CONTENT}}
</document>

<examples>
<example>
  <input>John will finish the report by Friday</input>
  <output>[John] Finish the report (Due: Friday)</output>
</example>
</examples>
💡 XML tags eliminate ambiguity about what is an instruction vs. what is data. Always use them for complex multi-part prompts.

4.3 Key Parameters

  • temperature — 0 (deterministic) to 1 (creative). Use 0 for code/facts, higher for creative tasks.
  • max_tokens — max tokens in response. Generation stops at this limit (stop_reason: max_tokens).
  • top_p — nucleus sampling (default 1.0). Rarely needs adjustment.
  • stop_sequences — stop generation when these strings appear.
  • stream — true for streaming SSE, false for batch.

4.4 Chain-of-Thought Prompting

  • Standard CoT — include reasoning examples: show input + reasoning + output
  • Zero-shot CoT — add "Think step by step" or "Let's reason through this"
  • Extended thinking — API feature giving Claude a dedicated thinking budget

CoT improves: math, logic, multi-step reasoning, code debugging. Use it for any task where intermediate steps matter.

4.5 Prefilling & Output Control

// Prefill to force JSON output
messages: [
  { role: "user", content: "List the top 3 risks." },
  { role: "assistant", content: "[" }  // <-- prefill
]
// Claude continues from "[", guaranteeing JSON array start

Other output control techniques:

  • Specify format in instructions: "Respond with only valid JSON"
  • Include a JSON schema or example in the prompt
  • Use stop_sequences: ["}"] to end after JSON closes

4.6 Few-Shot Prompting

Most effective for: specific output formats, niche styles, complex transformations hard to describe verbally.

<examples>
<example>
  <input>Translate to formal English: "wanna grab lunch?"</input>
  <output>Would you be available for lunch?</output>
</example>
<example>
  <input>Translate to formal English: "gonna be late ngl"</input>
  <output>I regret to inform you that I will be delayed.</output>
</example>
</examples>

<input>Translate to formal English: "{{USER_INPUT}}"</input>

Context Management
15% of exam · Context windows, prompt caching, token management, RAG
15%

5.1 Context Window

  • All current Claude models: 200,000 tokens
  • ≈ 150,000 words ≈ 500 pages
  • ~750 English words per 1,000 tokens
  • If prompt exceeds context window: API returns an error (no auto-truncation)
ℹ️ The Anthropic API is stateless — you must send the full conversation history on every request. There is no session storage server-side.

5.2 Prompt Caching

Cache stable prompt sections to reduce cost and latency:

// Mark content for caching
{
  "system": [{
    "type": "text",
    "text": "You are a helpful assistant with access to...",
    "cache_control": { "type": "ephemeral" }   // <-- cache this
  }],
  "messages": [...]
}

Key Facts:

  • Minimum cacheable size: 1,024 tokens
  • Cache TTL: 5 minutes (resets on each hit)
  • Max breakpoints per request: 4
  • Cache write cost: ~125% of input price (one-time overhead)
  • Cache read cost: ~10% of input price (90% savings!)

Usage Response Fields:

  • cache_creation_input_tokens — tokens written to cache (125% cost)
  • cache_read_input_tokens — tokens served from cache (10% cost)

5.3 Token Counting API

// Count tokens without generating a response
POST /v1/messages/count_tokens
{
  "model": "claude-sonnet-4-6",
  "system": "...",
  "messages": [...]
}
// Returns: { "input_tokens": 1423 }

Use before sending large requests to verify they fit in the context window and estimate costs.

5.4 Long Context Strategies

  • Sliding window — remove oldest messages when approaching limit. Simple but loses early context.
  • Summarization — compress older turns into a summary, replace them with it. Preserves semantic content.
  • RAG — retrieve only relevant chunks from a large corpus, insert into context. Most efficient for large knowledge bases.
💡 "Lost in the middle" — models attend less to content buried in the middle of very long contexts. Put critical instructions at the start and/or end of the prompt.

5.5 Extended Thinking & Tokens

  • Extended thinking generates <thinking> blocks before the final response
  • Thinking tokens are billed when generated; they become input tokens in subsequent turns if included in history
  • You can strip thinking blocks from history to save tokens (at the cost of losing reasoning continuity)
  • Total cost: input tokens + thinking tokens + output tokens

5.6 Caching Strategy Example

// Optimal cache layout for stable system prompt + variable queries
{
  "system": [{
    "type": "text",
    "text": "<large system prompt - 5000 tokens>",
    "cache_control": { "type": "ephemeral" }   // cached after first call
  }],
  "messages": [{
    "role": "user",
    "content": [{
      "type": "text",
      "text": "<reference document - 10000 tokens>",
      "cache_control": { "type": "ephemeral" }  // also cached
    }, {
      "type": "text",
      "text": "User's question here (changes each request)"
      // no cache_control — this varies
    }]
  }]
}
// Call 1: pays cache write for system + doc
// Calls 2+: pays 10% for system + doc, full price only for question
